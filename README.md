# MyWeb — система керування замовленнями, каталогом і відгуками

## 1. Опис проєкту

Проєкт розроблено в межах курсу «Технології .NET розробки web-додатків». Система демонструє організацію даних для інтернет-магазину з використанням реляційних баз даних Microsoft SQL Server та документної бази даних MongoDB.

Архітектура складається з трьох незалежних контекстів, кожен з яких відповідає за окрему частину предметної області.

## 2. Архітектура та контексти

### 2.1. OrdersDb — контекст замовлень

Відповідає за оформлення, зберігання, зміну статусів і скасування замовлень, а також за облік платежів та історії статусів.

Основні сутності:
- `Customers` — покупці;
- `Orders` — замовлення;
- `OrderDetails` — додаткові деталі замовлення;
- `Products` — дані про товари, необхідні контексту замовлень;
- `OrderItems` — позиції замовлення;
- `OrderStatusHistory` — історія змін статусу;
- `PaymentRecords` — записи про платежі.

Для роботи із замовленнями передбачено збережені процедури створення, отримання, перегляду замовлень покупця, зміни статусу, скасування та м’якого видалення.

### 2.2. CatalogDb — контекст каталогу

Відповідає за каталог товарів, їхні характеристики, зображення та категорії.

Основні сутності:
- `Products` — товари;
- `ProductDetails` — додаткові характеристики товарів;
- `ProductImages` — зображення товарів;
- `Categories` — категорії;
- `ProductCategory` — зв’язок товарів із категоріями.

Зв’язок між товарами та категоріями реалізовано через проміжну таблицю `ProductCategory`, яка містить власне поле `AddedAt`.

### 2.3. ReviewsDb — контекст відгуків

Реалізований на MongoDB та відповідає за відгуки покупців, обговорення, повідомлення й агреговані рейтинги товарів.

Основні колекції:
- `reviews` — відгуки, оцінки, автори та коментарі;
- `discussions` — обговорення товарів;
- `messages` — повідомлення в обговореннях;
- `productRatings` — агреговані рейтинги товарів.

У документах використовуються вбудовані дані (embedding), посилання між документами (referencing) та денормалізовані поля для зручного читання.

## 3. Структура репозиторію

```text
MyWeb/
├── README.md
├── docs/
│   ├── orders-erd.png
│   ├── catalog-erd.png
│   ├── contexts.md
│   └── documents.md
└── db/
    ├── p1/
    │   ├── schema.sql
    │   ├── procedures.sql
    │   └── seed.sql
    ├── p2/
    │   ├── schema.sql
    │   └── seed.sql
    └── p3/
        ├── collections.js
        └── seed.js
```

Файли в `docs/` містять діаграми зв’язків, опис контекстів і приклади документів MongoDB. SQL-скрипти та скрипти MongoDB зберігаються в каталозі `db/`.

## 4. Використані технології

- Microsoft SQL Server — реляційні дані замовлень і каталогу;
- T-SQL — створення таблиць, обмежень, індексів і збережених процедур;
- MongoDB — документи відгуків, обговорень, повідомлень і рейтингів;
- JavaScript для MongoDB Shell — створення колекцій, валідація документів, індекси, початкові дані та агрегації;
- Git і GitHub — зберігання коду та контроль версій.

## 5. Зв’язки та цілісність даних

У `OrdersDb` використовуються зв’язки один-до-одного, один-до-багатьох і багато-до-багатьох. Цілісність забезпечується первинними та зовнішніми ключами, унікальними обмеженнями, `CHECK`, `DEFAULT` та індексами.

Для аудиту передбачено історію зміни статусів. Для м’якого видалення використовується відповідне поле стану запису, а для оптимістичної конкурентності — `rowversion`.

У `CatalogDb` також використовуються всі три типи зв’язків, а таблиця `ProductCategory` дає змогу зберігати додаткові дані про зв’язок товару з категорією.

У `ReviewsDb` валідація структури документів виконується засобами MongoDB JSON Schema. Для підтримки типових запитів створюються індекси.

Між трьома базами даних немає зовнішніх ключів. Кожен контекст самостійно відповідає за власні дані.

## 6. Політика дублювання даних

| Дані | Основне джерело | Місце дублювання | Призначення |
|---|---|---|---|
| Назва товару | `CatalogDb.Products` | `OrdersDb` | Збереження назви товару в контексті замовлень |
| Ціна товару на момент замовлення | `CatalogDb.Products` | `OrdersDb.OrderItems` | Фіксація ціни під час оформлення замовлення |
| Назва товару для відгуків | `CatalogDb.Products` | `ReviewsDb.reviews` | Відображення інформації про товар без постійного звернення до каталогу |
| Назва товару в обговоренні | `CatalogDb.Products` | `ReviewsDb.discussions` | Зручне відображення обговорення |

Дублювання використовується для зменшення залежності між контекстами та прискорення читання. Ціни в позиціях замовлення мають зберігатися як історичний знімок і не змінюватися після зміни ціни в каталозі.

Для актуалізації скопійованих назв товарів у `ReviewsDb` необхідно передбачити механізм синхронізації, наприклад події або повідомлення між сервісами. Якщо такий механізм не реалізовано, актуалізація назв не є автоматичною.

## 7. Розгортання та запуск

### 7.1. SQL Server

Необхідно мати встановлений і запущений Microsoft SQL Server, а також інструмент для виконання T-SQL, наприклад SQL Server Management Studio (SSMS).

Для першого розгортання:

1. Відкрийте SQL Server Management Studio та підключіться до сервера.
2. Виконайте `db/p1/schema.sql`.
3. Виконайте `db/p1/procedures.sql`.
4. Виконайте `db/p1/seed.sql`.
5. Виконайте `db/p2/schema.sql`.
6. Виконайте `db/p2/seed.sql`.
7. Перевірте створені таблиці, зв’язки, індекси, процедури та тестові дані.

Якщо скрипти створення баз уже містять команди `CREATE DATABASE` і `USE`, окремо створювати бази вручну не потрібно. Перед запуском перевірте назви баз у скриптах.

### 7.2. MongoDB

Необхідно мати запущений сервер MongoDB та MongoDB Shell (`mongosh`).

1. Відкрийте `mongosh` і підключіться до сервера.
2. Виконайте `db/p3/collections.js` для створення колекцій, валідаторів та індексів.
3. Виконайте `db/p3/seed.js` для додавання початкових документів.
4. Перевірте документи, індекси та результати агрегованих запитів.

Скрипти слід виконувати в базі даних, назва якої вказана в їхньому вмісті.

### 7.3. Перевірка

Після розгортання потрібно перевірити:
- створення всіх таблиць і колекцій;
- правильність зв’язків і обмежень;
- роботу збережених процедур;
- обробку помилок і транзакцій;
- роботу валідації документів MongoDB;
- виконання індексованих запитів та агрегацій;
- повторний запуск seed-скриптів без небажаного дублювання даних.

**Примітка:** повторний запуск початкових скриптів без помилок можливий лише за умови, що вони реалізовані з перевірками існування об’єктів і захистом від повторного додавання даних.

## 8. Документація

У каталозі `docs/` зберігаються:
- `orders-erd.png` — ERD-діаграма бази замовлень;
- `catalog-erd.png` — ERD-діаграма каталогу;
- `contexts.md` — опис трьох незалежних контекстів;
- `documents.md` — приклади документів MongoDB та пояснення embedding і referencing.

## 9. Висновок

Проєкт демонструє розділення предметної області на три незалежні контексти, використання реляційної та документної моделей даних, обмежень цілісності, індексів, збережених процедур, транзакцій, аудиту та валідації документів.

Репозиторій призначений для демонстрації проєктування, розгортання та перевірки баз даних у межах лабораторної роботи з курсу «Технології .NET розробки web-додатків».
